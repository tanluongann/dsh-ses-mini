# dsh-ses-mini

A small **email surface for [DSH](https://github.com/deepseek-ai/deepseek-harness)**: the agent
is mailed at an address it owns, and it answers by email.

It exists for one concrete reason. Nelly normally talks to her owner through the Feishu/Lark
surface, and that tenant exhausted its monthly API quota — so this channel replaces the
transport while the agent stays the same: **inbound** polls the S3 bucket that AWS SES delivers
raw MIME into, **outbound** sends the turn's answer back through SES as a threaded reply.

The design assumption is that **a composed answer which is never delivered is the failure that
must never hide**. Everything below the config table follows from it.

```
  owner ──mail──▶ SES receipt rule ──▶ S3 object ──poll──▶ DSH session ──turn──▶ answer
                                                                                  │
  owner ◀──────────────────── SES SendRawEmail, In-Reply-To + References ◀────────┘
```

## Configuration

| key | default | effect |
|---|---|---|
| `mode` | `on` | `off` keeps the row mounted but inert |
| `awsRegion` | SDK default | region for both clients; empty = `AWS_REGION` / shared config |
| `mailBucket` | — | bucket the SES receipt rule writes to. Empty = dormant |
| `mailPrefix` | `inbound/` | key prefix of that rule's S3 action |
| `fromAddress` | — | the address answers come from. **Must be a verified SES identity.** Empty = dormant |
| `fromName` | — | display name on the From header |
| `replyTo` | — | optional `Reply-To` on answers |
| `operators` | `[]` | sender allowlist (addr-spec, case-insensitive). Empty = **anyone** who can reach the mailbox, logged loudly on every accepted message |
| `pollMs` | `30000` | S3 listing interval, clamped to ≥ 1000 ms |
| `maxPerPoll` | `10` | objects dispatched per poll, oldest first |
| `dedupTtlMs` | `1209600000` (14 d) | how long a `Message-ID`/object key is remembered — and the age at which unprocessed mail is left alone |
| `seenMaxEntries` | `2000` | cap on the persisted seen set, oldest evicted first |
| `maxBodyChars` | `20000` | inbound body handed to the model, with a truncation marker |
| `maxMessageBytes` | `10485760` | refuse to download an S3 object larger than this |
| `signature` | — | appended under an RFC 3676 `-- ` delimiter |
| `includeQuotedOriginal` | `false` | quote the message being answered under the answer |
| `quoteChars` | `1200` | characters of that quote |
| `logPath` | `<cwd>/logs/ses-mail.log` | where the event log is appended (relative = from `cwd`) |
| `cwd` | profile cwd | where new sessions start, and where the log lives |
| `provider` / `model` | host default | route for sessions this surface creates |
| `steerMidTurn` | `true` | mail arriving while a turn runs steers it instead of queueing |
| `sessionId` | — | pin every correspondent to ONE session (`''` = one session per sender) |
| `instance` | `mail-<from local part>` | namespace for the state file and derived session ids |

**No credential is ever configured.** The S3 and SES clients are built with no explicit
credentials, so the SDK resolves them from the standard chain — `AWS_*` environment variables,
the shared config file, the SSO cache, or the instance/task role. A secret in a config file is a
secret in a profile patch, in the repo and in the shell history.

## Inbound

1. Every `pollMs`, `ListObjectsV2` pages the whole prefix (SES key templates are not
   time-ordered, so "new since the last poll" cannot be a listing parameter).
2. Objects already in the seen set are skipped without a download. Objects older than
   `dedupTtlMs` are skipped and recorded: past that age the dedup identity may already be
   forgotten and a stale question has no answer worth sending.
3. Bytes are parsed with `mailparser`; the identity for dedup is `Message-ID`, or the S3 key
   when a sender omits the header.
4. Policy runs in this order — **own address** (a loop straight back to us), **automated**
   (`Auto-Submitted`, `Precedence: bulk|junk|list`, `List-*`, `X-Autoreply` /
   `X-Auto-Response-Suppress` / `X-Autogenerated`, a null `Return-Path` i.e. a bounce, and a
   subject that looks like an out-of-office), then the **allowlist**, then content. A refused
   message is logged with the header that matched, is never answered (replying to a stranger is
   backscatter and replying to an autoresponder is how a loop starts), and is remembered so it
   is not re-refused on every poll.
5. What is left becomes a turn: one conversation per correspondent, `followup()` when idle,
   `steer()` into the running turn when not.

Quoted history is stripped before the model sees it — the session already carries the
conversation, and an email client that quotes the whole thread would otherwise re-inject it
every message. The cut is deliberately conservative: a bottom-posted reply (words *after* the
quote) and an inline reply are recognised and passed through whole, because trimming too eagerly
would lose the human's own words. The log line records `chars=` (what the model saw) and
`raw-chars=` (what arrived).

## Event table (CHANNEL-CONTRACT §3/§6)

| Event | Lane | Notes |
|---|---|---|
| `user.message` (accepted mail) | **turn** | one turn per mail; automated/list/bounce refused before it |
| `steer` (mail arriving mid-turn) | **steer** | `steerMidTurn` |
| bounce / receipt | **state** | logged, never wakes the model |
| `agent.alert` / `agent.note` | **outbound** | emit via `<cwd>/channel-outbound/` spool (`channel-emit.py`); alert immediate, note rate-limited |
| `agent.chatter` | **held** | email mapping: never sent (chatter-never), held visibly |

New config keys (contract §2/§4): `outboundPrimaryChat` (owner address for
`to: "primary"`), `politenessQuietHours`, `politenessNoteRatePerHour`,
`politenessDedupWindowMinutes`, `politenessChatter` (default `never` for this
transport), `reasoningEffort` (provider-gated, contract §2).

## Outbound

On `turn/end` the answer — the text of the last non-empty `assistant/message` — becomes a raw
MIME message built by hand (`lib/mail.js`) and sent with `SendRawEmail`:

* `To` is the sender of the mail being answered, `Subject` is `Re: …` exactly once;
* `In-Reply-To` is that message and `References` is the whole chain, root first, which is what
  lands the reply in the original conversation in clients that thread by References;
* `Auto-Submitted: auto-replied` marks **our** output, so if it ever comes back to the mailbox
  the inbound guard refuses it on that header alone;
* the body is base64 — model output is arbitrary UTF-8 with arbitrary line lengths, and a line
  over 998 octets is illegal in SMTP;
* every header value is flattened to one line first: an RFC 2047 subject that *decodes* to a
  CRLF is exactly how a `Bcc:` gets injected, and that is the one place model output meets a
  protocol where a newline is a delimiter.

A turn with no inbound mail behind it (a cron job resuming the same session, for instance)
sends nothing, and a turn is never answered twice.

## Running the tests

```bash
npm install
node scripts/link-closure.mjs   # point @deepseek-ai at the installed dsh closure
node test/harness.mjs           # unit: config, guards, MIME, dedup, bot policy, transport
node test/integration.mjs       # end-to-end through the real cordis registry, AWS faked
```

No network, no AWS account, no credentials: both suites use the `deps.s3` / `deps.ses` seams
(the SDK's own `{ send(command) }` shape) and fixture `.eml` files in `test/fixtures/`.

## Install into a profile

```bash
cd ~/.dsh/repos/dsh-ses-mini && npm install && node scripts/link-closure.mjs

# ~/.dsh/profiles/<profile>/package.json
#   "dependencies": { "dsh-ses-mini": "link:/home/<you>/.dsh/repos/dsh-ses-mini" }
#   "dsh": { "profile": { "bundles": ["@deepseek-ai/dsh-base", "dsh-ses-mini"] } }

# ~/.dsh/profiles/<profile>/cordis.patch.yml
#   - id: ses-mini
#     config:
#       awsRegion: eu-west-3
#       mailBucket: my-inbound-mail
#       fromAddress: nelly@example.com
#       fromName: Nelly
#       operators: [owner@example.com]
#       cwd: /home/<you>/.dsh/<agent>

dsh plugin --profile <profile> install
systemctl restart dsh-<profile>.service
```

AWS side: a verified SES identity for `fromAddress` (sending), a receipt rule that delivers to
`mailBucket` under `mailPrefix` (receiving), and an IAM policy allowing
`s3:ListBucket`/`s3:GetObject` on that prefix plus `ses:SendRawEmail` from that identity.

## Operational notes

* **The log is the observability, not the logger.** The DSH logger's output does not reach the
  service's stdout, so `<cwd>/logs/ses-mail.log` is where the truth is: `ARMED`, one `INBOUND`
  per message, `REFUSED reason=…`, `DISPATCH`/`STEER`, `TURN-END`, `SEND ATTEMPT`, `SENT`,
  `SEND FAILED` (with SES's own error text), `UNDELIVERED`. Diagnose a silent mailbox by
  checking for the `ARMED` line first: no `ARMED` means the row never started, not that no mail
  arrived.
* **A failed send is kept, not just logged.** SES refusals and non-retryable errors write the
  composed message to `<cwd>/logs/undelivered/<timestamp>.eml`, byte for byte, so an operator
  can resend it as it stands (`aws ses send-raw-email --raw-message file://…`). Throttling and
  5xx get exactly one automatic retry first.
* **Dedup is persisted and bounded.** `ses-mini-<instance>.json` in the *profile* directory
  holds the correspondent → session bindings and the seen set, so a restart neither re-answers
  yesterday's mail nor starts the owner with no history. Two mailboxes in one profile cannot
  collide: the file name carries the instance.
* **Sandbox caveat.** The plugin runs inside the DSH service, not inside an agent's file
  sandbox. Its writes are best-effort by design (a read-only profile directory must not kill the
  poll loop), so under a sandbox that denies writes outside the workspace an unwritable
  `logPath` or `cwd` fails *silently by construction*. Point `cwd`/`logPath` at a directory the
  service can write, and confirm the `ARMED` line appears after a restart. Outbound S3/SES also
  needs network egress: a sandbox with no egress produces `SEND FAILED`, which is exactly what
  the log will then show.
* **Never reply to refused mail.** It is the reason a list, a bounce or an autoresponder cannot
  turn this surface into a mail loop.

## Deliberately not implemented

* **No command layer.** Mail is dispatched to the agent as-is; a `/stop`-style surface would
  have to guess whether a leading `/` is a command or the start of a sentence, and guessing
  wrong means silently not answering a message. Stop a turn through the agent's own surfaces.
* **No attachments, either way.** Inbound attachments are not read (a message with no text part
  is refused with that reason), and answers go out as `text/plain` only.
* **No HTML.** Answers are plain text (base64-encoded UTF-8); an HTML alternative is not built,
  because the one thing this channel must get right is which text the model wrote, and a second
  rendering is one more thing that can disagree with it.
* **No `Reply-To` following.** The answer always goes to the `From` address. Honouring an
  inbound `Reply-To` means a stranger can choose where the agent's answer lands, which is a
  loop and a spam vector for no gain in the common case.
* **No live progress surface.** Email has nothing to patch between "received" and "answered";
  the Feishu surface's card, beat and reactions are absent rather than stubbed.
